## 结论与范围

建议建设一个独立的 WebGPU 园区版本，保留“由参数和代码生成全部场景资产”的方式，采用 Three.js 0.186.1 的节点材质、TSL 和 RenderPipeline。复用现有布局及几何生成规则，重建光照、材质、可见性和时域渲染；首版不引入 Rust，不自研通用渲染引擎。

推荐最终规模为现有现代园区的完整升级：总部、研发 A–D、园区客厅、展示中心共七栋建筑，两庭院、柱廊、入口与步道、屋顶设施/种植、外围林地和相连背景。保留自动漫游、自由探索、画质切换和截图。完整庭院加两栋建筑是先期验证阶段，不是最终交付范围。

这里的“不用建模”指不需要在 Blender 等工具中手工制作、导入模型；运行时仍由代码生成真实三维几何，才能产生透视、遮挡、阴影和反射。WebGPU 与这种程序化生成方式兼容。

“写实仿真”在此定义为：真实米制尺度、构造合理、光照与材质响应可信，在步行、横移和近看中保持成立。它不等于建筑结构验算、照度认证或植物力学/生长科学模型。不需要外部 3D 模型、照片纹理或外部 HDRI；程序自身产生的纹理、远景表示和缓存仍属于程序化资产。真实照片可作设计参考。

这些是供开工决策的设计与验收目标，不能理解为新版已经实现，或其性能已经得到证明。

| 专家方向 | 独立产出 | 交叉评审后的关键判断 |
| --- | --- | --- |

| 性能与验证 | [performance-validation.md](webgpu-analysis/performance-validation.md) | GPU 优化要以同画面、同负载的净收益为准；兼顾反射/阴影可见性和实例历史。 |

三路先独立形成报告，再阅读其他报告、反驳关键假设。以下争议已收敛：

- **全量堆叠效果还是先建立光照基准？** 选固定晴日、直接阴影、受控世界空间间接光、局部镜面反射和经过验证的抗锯齿。SSR/SSGI 不作为首版正确性的前提。
- **内置探针能否直接使用？** 其烘焙器和 atlas 可用，但与天空及多个网格直接叠加会重复贡献漫反射。需要有限的自定义 TSL 混合，不能通过降低整体曝光掩盖。
- **一面平面反射能否覆盖园区？** 只允许作为第一试验的预算。最终按当前自由相机选择可见平面，角部同时看见两面时须验证；不能只照顾固定运镜。
- **TRAA 是否必然更好？** 必须与空间抗锯齿比较清晰度、闪烁和拖影。不能用模糊换取一张干净截图。
- **是否先做复杂 GPU 裁剪？** 先有可比较的普通实例版本，再验证植物簇级计算裁剪、压缩列表与间接绘制；收益不成立就保留简单路径。

性能专家进一步反驳了“TRAA 可以直接列为必选主线”：玻璃表面的运动向量不能代表倒影的运动，反射面的调度也不一定反映在主深度中。最终裁决是**先建立空间抗锯齿基线，再决定 TRAA 是否进入默认路径**；P0/P1 必须包含玻璃与时域的组合实验。

最终方案审查另纠正了一项归因：本地 `LightProbeGridWebGL` 也已支持GPU驻留烘焙和零CPU回读，因此该能力属于两种后端都可采用的基础设施，不算WebGPU独有收益。

## 投入优先级与 Rust 的位置

| 优先级 | 要做的事 | 预期改善与保留条件 |
| --- | --- | --- |
| 先做 | 校准天空/太阳能量、玻璃反射和接触层次；保留原有叶片裁切、纹理尺度与构造细节 | 解决已观察到的视觉问题。必须在完整画面、近景及运动中成立，不能靠曝光掩盖错误。 |
| 先做 | 生成放入Worker；复用几何/材质/纹理；调查管线变体与编译；建立带版本的生成缓存 | Worker主要降低主线程阻塞，不保证总生成时间下降；缓存主要改善后续加载。分别测量可交互时间与完整首帧。 |
| 随后做 | 空间分块、投影尺寸LOD、反射按失效条件更新 | 降低每帧实际工作量，属于WebGL/WebGPU都能使用的优化。先建立完整普通实例基线。 |
| 实验后决定 | GPU簇级剔除与间接绘制、compute程序纹理、TRAA | 分别证明同画质净收益；无收益或造成漏影/拖影就不进入默认路径。 |
| 暂不投入 | Rust/Wasm重写 | Rust不会让现有GPU shader自动变快。只有Worker和缓存后，剖析仍确认CPU几何生成是主要瓶颈，且跨边界传输成本可控，才挑独立热点做小规模对照。 |

目前没有证据支持“换WebGPU就提高几倍”或“换Rust即可明显提升画质”。本方案投资的重点是减少重复工作并改善光照/材质模型，而不是更换语言本身。

## 写实表现主线

### 建筑、地面与植物

延续现代矿物墙面、玻璃幕墙、克制金属与木檐的方向。真实几何负责轮廓、窗洞、檐口、台阶、近景倒角和深缝；材质负责毛孔、细木纹、浅划痕、微粗糙度。大尺度批次差异、中尺度加工方向和微尺度表面必须有各自来源，不能只铺一层随机噪声。

视觉专家已查看Apple Park及Google Bay View的官方项目照片，提取玻璃/室内同时可读、木檐与铺装节奏、群落种植、浅色构件光照层次四项参照。它们只是表现标准，不复制其标志性建筑，也不导入照片资产；直接来源与观察记录见[视觉报告](webgpu-analysis/visual-realism.md)。

近景玻璃需要框、胶条、边缘厚度和有限的真实可见室内。远层允许沿用程序室内视差表示，但过渡不能暴露为纸片或黑板。窗格不应全部变成镜子。

植物使用连贯父子枝系、根颈与枝叶连接；色差与个体、枝系、叶龄相关。近景为真实叶片，中景为枝叶簇，远景可使用由同一生成树烘焙的多视图表示。所有等级保持冠幅、颜色与透光关系。LOD 依据投影尺寸而非固定世界距离，带滞回；过渡策略需与时域抗锯齿一起验证。

细节必须按像素足迹过滤。光照和几何接触先成立，再加入接触 AO；不能靠更黑的 AO 隐藏悬浮、漏光和错误构造。[纹理采样依据](https://pbr-book.org/4ed/Textures_and_Materials/Texture_Sampling_and_Antialiasing)

### 光照与反射

1. 程序天空与太阳共享方向、颜色和能量基准；主环境捕获去掉太阳圆盘，避免与直接太阳重复计数。先固定一个晴日条件，关闭逐镜头自动曝光。
2. 先验证 `SunLight` 的级联阴影与自由相机；影图随有效视域变化，不能照搬旧版完全冻结影图的策略。近景接触、远景树冠和级联切换都必须成立。
3. 复用 `LightProbeGrid` 的 GPU 烘焙与 atlas 数据。网格按照庭院、廊下和薄墙边界分区，在简化的独立静态场景中分批捕获；网格完整 ready 后再渐入。
4. 主场景不同时挂自动累加的 probe lights。通过局部 TSL 环境节点实现“廊下探针优先、庭院补足、天空兜底”的归一化混合，保留镜面环境与多重散射路径。具体公式及源码依据见架构报告第二轮。此定制依赖 r186 节点契约，需锁版本和升级回归。
5. 镜面基础为程序天空与空间校正的局部反射探针；近景、大屏幕面积、低粗糙度玻璃优先分配平面反射。同平面的窗格共享捕获，镜面来源按权重替换，不等强相加。

内置探针具备 GPU 驻留烘焙，但不是自动具备可见性判断的动态全局光照。薄墙漏光、网格重叠和法线偏移是开工后优先实验项。[LightProbeGrid](https://threejs.org/docs/pages/LightProbeGrid.html)

还要控制其实际成本：本地实现每个网格每次求值涉及7次3D atlas采样，不能把全园区所有网格接入所有表面，再期待零权重自动消除采样。按空间块绑定有限候选（先局部加背景），保持绑定布局稳定；新增候选必须测量。每探针至少采集立方体六面，若沿用旧版907探针即至少5,442次面捕获，尚未计球谐投影/打包。分批过小还可能重复刷新阴影，因此应根据实测成本选择批量，而非仅按探针数猜测启动速度。

### 时间稳定性

初始默认使用 HDR 与4倍MSAA空间抗锯齿，TRAA作为可切换实验。TRAA路线输出所需深度/速度并关闭MSAA；只有动态对照通过才考虑替换默认。SSR/SSGI 的效果降噪与全画面抗锯齿分别验收。

先比较四组相同场景：“空间抗锯齿/TRAA”乘以“平面反射关闭/开启”，覆盖沿玻璃横移、两反射面轮换和微风树木倒影。本地 TRAA 没有可直接假定存在的反应性遮罩输入。若主表面速度不足以表达倒影，需先验证有限的历史抑制或分层处理；成本或质量不成立则使用空间抗锯齿，不把拖影方案作为默认交付。

风动、billboard 转向、GPU 实例重排必须通过稳定实体 ID 获得正确前帧状态。相机切镜、重建场景、改分辨率及光照突变要明确失效历史；不能假定存在可直接调用的通用 reset。静止画面收敛后休眠，恢复操作时重启；若微风仍在运行，就不能复用过期画面。

先无风校准，再加入可重复的轻微风动，并同步阴影/反射。连续昼夜、复杂天气、风力学求解、全路径追踪、强景深与运动模糊不列为首版必要条件。它们不应挤占完整园区和基本写实的预算。

## WebGPU 特有路径与通用优化

| 路线 | 具体实施 | 证明收益的方式 |
| --- | --- | --- |
| 植物簇级 GPU 可见性 | CPU 先做粗分区；GPU 判断视锥/屏幕尺寸，按物种、材质、LOD 压缩稳定 ID，生成间接命令 | 对比同一 WebGPU 场景的普通实例路径，计入 compute、命令生成和所有视角绘制总成本。 |
| GPU 驻留程序纹理 | 树皮、噪声、法线、粗糙度候选由 compute 生成并建立 mip，材质直接使用 | 比较 CPU 加上传、离屏片元烘焙、compute 三条等质量路径；不为一次性小纹理强加复杂度。 |
| GPU 驻留光照烘焙（通用） | 探针采集、球谐投影和 atlas 打包在 GPU 内完成，分批调度；旧WebGL实现也已具备 | 检查峰值内存、调度和可交互时间，并确认光照校准通过；不声称消除了旧版原本就没有的CPU回读。 |
| 数据往返及带宽（通用原则，含WebGPU实现） | 静态实例参数留 storage buffer；仅更新小量参数，共享必要深度/速度输出，池化目标 | GPU 分 pass 计时与资源账本；不能把打开更多 MRT 本身当优化。 |

主相机、各阴影视角和反射相机分别拥有可见集合，或采用经过证明的保守集合；主画面不可见的树仍可能投影或倒映。风摆和 LOD 过渡必须扩展包围体。先做到零遗漏，再争取更小集合。

列表缓冲可按严格的pass顺序复用，不能在还会被消费时覆写。可见性使用无抖动视锥加保守边界，避免抗锯齿抖动引发物体忽隐忽现；实体历史每个显示帧只推进一次，不能主视角、反射和阴影各推进一次。

裁剪用“计数清零→可见性/压缩→间接命令→绘制”的有序阶段，不能依赖工作组屏障实现全局同步。零实例、容量上限和重排都要测试。第一版不做逐叶原子压缩、全园区 Hi-Z、subgroups/f16 特化；它们只能在明确热点出现后新增实验。

程序生成缓存、Worker、分块、LOD 和静态反射复用都值得做，但属于通用优化，不能全部记为 WebGPU 带来的收益。[间接绘制接口](https://threejs.org/docs/pages/BufferGeometry.html)

专属实验的重点是WebGPU的compute/storage/indirect具体路径；“数据留在GPU”和“减少带宽”本身并不专属于WebGPU。[现有WebGL探针实现](../node_modules/three/examples/jsm/lighting/LightProbeGridWebGL.js)同样声明并实现零CPU回读烘焙。

## 代码与数据组织提案

独立实验已建立 `campus-webgpu.html`、`src/campus-webgpu/` 和部分验证工具，原入口保持可用。先锁定已核对的版本；验证期间不同时升级引擎。以下是最终职责划分，文件存在不代表对应能力已完成验收：

```text
campus-webgpu.html
src/campus-webgpu/
  main.js                 启动、界面、能力检查
  world/build.js          布局与几何规则，输出分块数据
  world/worker.js         分批生成与可取消任务
  scene.js                资源装配、材质/纹理共享、资源所有权
  materials.js            标准/物理节点材质与程序表面
  lighting.js             天空、阴影、受控探针和反射区域
  visibility.js           普通实例基线及 GPU 可见列表
  render.js               RenderPipeline、历史、调度与测量
```

生成、资源装配、渲染三个深模块分别隐藏内部复杂度：

- `buildWorld(spec, {signal,onChunk})` 输出米制分块包围盒、各级几何、材质编号、稳定实例 ID 与数组。CPU/Worker 处理复杂建筑和枝系拓扑；结果不持有 renderer 或材质。
- `createScene(chunks, renderer)` 管理上传、节点材质、光照区域、共享资源与 `dispose()`，避免生成器参与 GPU 生命周期。
- `createView(renderer, scene)` 管理每帧、尺寸、画质、时域历史与测量；UI 只表达相机和状态变化。GPU 裁剪是内部可切换路径，不建立泛化多后端框架。

缓存键至少覆盖种子、参数、生成器版本和数据格式；光照缓存另含太阳/天空/遮挡几何/烘焙设置。持久化 TypedArray 或自生成纹理数据，不持久化 GPU 对象。GPU 生成数据要跨会话缓存时，单次导出与读回成本单独测量；正常帧不读回实例数驱动绘制。

## 建议验收标准

### 视觉

固定 1920×1080、相机/FOV、种子、太阳方向、色调映射和白平衡。先用灰片校准两套光照，再锁曝光；相同曝光数字不自动意味着相同照明。分别保存实时连续帧、刚停止画面、注明累计时长的静止图，不能用静止图代表实时质量。

| 检查 | 观察条件 | 判退反例 |
| --- | --- | --- |
| 玻璃与柱廊 | 眼高约1.7m、距玻璃约1m、横移至少3m，并观察建筑角部 | 反射粘在玻璃上、物体出主视角即丢失、分区接缝、统一黑板式玻璃。 |
| 光照与接触 | 晴地走入檐下，经过薄墙/柱脚/树根 | 穿墙亮斑、取景改变使哑光面跳亮、悬浮接触、重叠探针增亮。 |
| 植物与地面 | 树干约0.8m、灌木约0.5m；逐步退到10/30/80m | 断枝、根部滑动、树冠/透光突变、草坪整片变色或消失。 |
| 运动与切镜 | 每段至少10秒，约1m/s步行，含缓转、骤停、切镜与微风 | 正常播放可见双影、拖尾、细缝爬动、残留上一镜头内容。 |
| 完整覆盖 | 七栋可达立面、两庭院、六段漫游、屋顶俯视及外围 | 只有样板庭院写实、换楼穿帮、背景露出边缘、降档丢失整株投影/倒影。 |

这些是拟定判据。光照误差与时域指标的数值容差在 P0 按采样误差标定；不会用单个截图相似度分数代替上述视觉判断。

### 性能与稳定性

参考设备为当前 Apple M4 Pro，目标是原生 1080p 的稳定 60Hz 体验。建议初始预算：GPU 总时间 p95≤14ms、CPU 提交 p95≤4ms，另查实际 RAF 的 p95/p99 和卡顿；两项耗时可能重叠，不能简单相加推出 FPS。应用可核算 GPU 资源建议≤768MiB，不能当作驱动总显存实测。

完整画面的首次应用缓存空启动建议≤10秒、重载≤3秒，生成阶段主线程任务目标≤50ms；首个有意义画面、可交互画面和完整画面分别记录。网络条件单列；浏览器/驱动编译阻塞独立归因。以上是需要实验验证的目标，尚不是承诺。不能为了达标把低模占位画面记为完整画面。

预热后至少三轮交错 A/B 完整漫游，记录浏览器/系统、供电、刷新率、DPR、实际 render target 尺寸、代码哈希和种子。GPU 时间使用可选 timestamp-query 异步解析，CPU 提交与 RAF 另报。没有 GPU 查询时必须注明证据限制，不能使用 `gl.finish` 或提交 Promise 的耗时冒充纯 GPU 时间。

GPU 剔除的间接实例数需独立诊断：小场景离线回读列表/命令，与 CPU 正确集合比对。本地 Three 的普通 `renderer.info` 三角形统计不等于间接绘制的真实数量。

单项复杂优化的建议保留条件：至少两个代表视角总 GPU 时间改善≥10%或≥1ms，其他视角不恶化超过5%，且视觉门槛全部通过。接近噪声的差异增加样本；没有收益保留简单路径，不为使用 compute 而保留复杂实现。GPU 驻留烘焙、计算纹理和可见性各自归因，不能用一个成功例子证明所有优化。

资源生命周期检查包括至少10次切画质/重建、前后台恢复、窗口改变、设备丢失及恢复；等待稳定后资源数量不能持续增长。不把一个 M4 Pro 的结果外推到 Windows、Safari 或移动设备，这些要独立建档。

### 访问与能力

当前 `http://100.110.84.28:5173/campus.html` 是非 localhost 的 HTTP 地址。新版本远程访问应提供可信 HTTPS；本机开发可以使用 localhost。本轮不修改网络或证书设置。

检查安全上下文、`navigator.gpu`、初始化结果，再验证 `renderer.backend.isWebGPUBackend`。WebGPURenderer 类名不足以证明实际后端，因为默认可能回退 WebGL2。记录真实 device 的 adapterInfo、features、limits 和 compatibilityMode；缺失字段记未知。若能力不足，说明原因并提供原版链接，由用户选择访问，不能把静默回退版标为 WebGPU。[官方迁移与后端说明](https://threejs.org/manual/pages/webgpurenderer)、[安全上下文](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)

## 决定继续实施时必须验证的假设

1. **受控探针是否足以覆盖全部廊下与薄墙？** P0校准和P1真实空间会决定分区、代理精度及是否需要额外静态可见性数据。
2. **有限平面反射是否满足自由探索？** 角部同时可见多面时，若视差不成立，要增加有效预算或调整表示，不能限制原定可达范围来掩盖。
3. **TRAA能否兼顾细叶清晰度和运动？** 与无时域空间基线并排比较，失败则先修历史状态，不能以模糊替代。
4. **GPU簇级裁剪是否有净收益？** 普通实例基线和全量七栋场景给出答案；逐叶处理和Hi-Z不提前立项。
5. **启动与内存预算是否可达？** 应用缓存、管线编译和烘焙分别计时；不可控驱动缓存不作为保证。

推荐开工顺序是 P0→P1，建立可复现的写实基线后再推进 P2/P3，最后完成 P4。完整园区与写实质量始终是终点，技术演示与单镜头成绩只能作为中间证据。
